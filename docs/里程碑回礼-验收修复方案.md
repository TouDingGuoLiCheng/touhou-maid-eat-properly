## 4. C1–C2 — 公屏话术（本会话已实现）

### 4.1 根因

| 问题 | 说明 |
|------|------|
| **时间源不一致** | 本模组 `MaidSpeech` 用 `level.getGameTime()`；车万女仆 GUI（`ScheduleButton`）用 `level.getDayTime()`。用 `/time set` 或部分测试场景下两者**不同步** → GUI 显示白天，公屏逻辑却判成夜间并排队。 |
| **固定 10:00 投递** | 窗口外消息统一排到「次日 10:00」同一 `gameTime`，`tickPendingChat` 到点**批量发出**（多只女仆 / 多次指令更明显）。 |
| **owner 离线** | 队列里消息在 owner 非 `ServerPlayer` 时会一直保留，之后上线到点才爆发（次要因素）。 |

**TLM 时间换算（与 GUI 一致）**：

```java
long dayTime = level.getDayTime() % 24000L;
int hour = (int) ((dayTime / 1000 + 6) % 24);
int minute = (int) ((dayTime % 1000) * 60 / 1000);
```

### 4.2 修复（已定稿）

#### A. 统一时间源

- 公屏窗口判断、延迟投递、队列 tick **全部改用 `level.getDayTime()`**（不再用 `getGameTime()`）。
- 新增 `MaidWorldTime`（或同类工具）封装上述 TLM 公式，供 `MaidSpeech` 调用。

#### B. 公屏可发送窗口

- 使用 **08:00–20:00**（按 TLM `dayTime` 刻度：`tod` ∈ [2000, 14000)）。
- 窗口内：`speakToOwner` **立即**发公屏 + 气泡。

#### C. 窗口外延迟投递

- **不再**固定次日 10:00。
- 每条排队消息独立随机一个 **08:00–20:00** 内的 `dayTime` 刻度投递点（用女仆 `RandomSource`，避免同一时刻爆发）。
- 存储：队列 `AT` 改为**下一次触发的绝对 `dayTime`**（`nextRandomDeliveryDayTime(currentDayTime, random)`），`tickPendingChat` 用 `getDayTime()` 比较。
- 若到点仍不在 08:00–20:00（边界情况），重新 roll 下一个随机点。

#### D. 话术优先级（沿用上轮共识）

| 类型 | 公屏 |
|------|------|
| **窗口内立即** | 里程碑送礼、新索要（自然 / `/ep request now` / 加餐许可）、催眠便签、完成感谢、放弃索要 |
| **窗口外 → 随机延迟** | 同上（进队列，非固定 10:00） |
| **仅气泡** | 里程碑重复 nag（`bubbleOnly`）、周期性催促 nag、饥饿抱怨（可延迟或仅气泡——**催促/饥饿窗口外也走随机延迟队列**） |

#### E. 实现触点

- 重构 `MaidSpeech`：`isChatWindow`、`enqueuePendingChat`、`tickPendingChat`、`nextDeferredDeliveryTime`。
- `FoodRequestHandler.tickMaid` 已每 20 tick 调 `tickPendingChat` — 保持。
- 单元测试：`getDayTime` 与 TLM 公式、`/time set` 模拟、随机投递不共用一个 `AT`。

### 4.3 验收标准

- [ ] GUI 日程按钮显示 08:00–20:00 内 `/ep favor setlevel` 跨档 → 立刻公屏 + 气泡。
- [ ] `/ep request now` 白天立刻公屏（与 GUI 时间一致）。
- [ ] 窗口外触发 → 不在同一 tick 爆发多条；投递时刻落在 08:00–20:00 之间。
- [ ] `/time set` 后行为与女仆 GUI 显示时间一致。

## 5. P1–P2 — 持续效果 / 性能（本会话已实现）

### 5.1 现象与根因

| 效果 | 当前实现 | 问题 |
|------|----------|------|
| **夜雀糖纸**（夜视） | 每 tick 检查；duration ≤ 200 时 `addEffect(220)` | 条子停在 ~11 秒附近抖动；**每 tick 都在判 + 周期性 addEffect** |
| **银铃挂饰**（迅捷 I） | 同上，逻辑与夜雀糖纸一致 | 同上 |
| **幸福 BUFF** | 12000 tick 正常递减 + 每 20 tick 回饥饿 | **无高频刷新**；若条子不动，多半是同时戴着夜视/迅捷 |

### 5.2 修复原则（已定稿）

- **保留状态栏图标**（夜视、迅捷 I 效果图照常显示）。
- **短时长可见递减**（玩家能看到倒计时往下走，不是钉死在同一秒数）。
- **夜雀糖纸与银铃挂饰同一套逻辑**。
- **禁止高频刷新**：仅在效果**即将结束**时补一次，不要「阈值内每 tick 重置」。

### 5.3 具体实现

**夜雀糖纸 + 银铃挂饰（统一）**：

```text
佩戴中：
  若无对应 MobEffect，或 remainingDuration ≤ REFRESH_THRESHOLD（建议 20 tick）：
    addEffect(duration = REFRESH_DURATION, 建议 6000 tick ≈ 5 分钟显示)
  否则：本 tick 不做任何事（不 addEffect）
摘下 / 不在玩家饰品槽：
  removeEffect（夜视 / 迅捷）
```

- 去掉现有 `duration > 200` 仍每 tick 进入判断后频繁 `addEffect(220)` 的行为。
- `REFRESH_THRESHOLD = 20`：快消失才补，**绝大多数 tick 零开销**。
- `REFRESH_DURATION = 6000`：条子能肉眼看见递减；仍属「短效条」相对整局，但比 11 秒更自然。

**幸福 BUFF**：

- 逻辑不改（10 分钟 + 每秒回饥饿）。
- 回归时**不戴**夜视/迅捷单独测；若仍异常再查客户端。

**其他饰品 tick**（绯想属性修饰符、保温餐袋 exhaustion、月见糖进度等）：

- 维持现状；已属低频或无 BUFF 条。

### 5.4 性能预期

| 饰品 | 修复前 | 修复后 |
|------|--------|--------|
| 夜雀 / 银铃 | 每 tick 读 effect + 周期性 addEffect | 每 tick 仅读 effect；addEffect 约每 5 分钟一次 |
| 幸福 | 每 20 tick 回饥饿 | 不变 |

### 5.5 验收标准

- [ ] 戴夜雀糖纸：夜视图标在，倒计时**可见递减**，不会钉死在同一数字。
- [ ] 戴银铃挂饰：迅捷 I 图标在，同上。
- [ ] 摘下后效果消失。
- [ ] 不戴夜视/迅捷时，幸福 BUFF 倒计时正常递减。
- [ ] （可选）Profiler 下佩戴夜视不再每几秒刷一次 `addEffect`。

```

```

- 权限：与 `/ep satiety set` 同级（`requires(2)`）。
- 挂到 `eatproperly` 与 `ep` 两棵命令树下（与现有子命令一致）。

**不做**：`hunger add`、指定其他玩家、改饱和度等扩展。
